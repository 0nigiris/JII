> Этот файл — «библия проекта» для владельца: прочитав его, ты сможешь ответить на
> любой вопрос о JII — что это, как устроено, почему сделано именно так, где что

> здесь — то же самое плюс история решений и готовые ответы, человеческим языком.

## 1. Что такое JII — питч за 30 секунд

**JII («Just Install It») — умный универсальный установщик программ для Linux.**

Проблема: в Linux один и тот же софт живёт в десятке мест — репозитории дистрибутива
(dnf/apt/pacman…), Flathub, Snap Store, COPR, AUR, crates.io, npm, PyPI, GitHub
Releases, Homebrew, Nix… Новичок не знает, откуда ставить; опытный — тратит время на
перебор. Каждый источник — свой синтаксис, свой уровень доверия, свои грабли.

Решение: пользователь думает о **программе**, а не о пакетных менеджерах:

```console
$ jii docker
```

JII параллельно ищет по **всем** источникам, которые есть на машине, **ранжирует**
результаты (доверие, приоритет, здоровье источника), **рекомендует** лучший вариант,
**объясняет почему**, показывает точный план действий и устанавливает — спросив ровно
столько подтверждений, сколько требует уровень доверия источника.

**Ключевая фраза: JII — это установщик, НЕ пакетный менеджер.** Он не хранит пакеты,
не разрешает зависимости, не подменяет dnf/apt. Он **дирижирует** менеджерами,
которые уже стоят, и всегда говорит, что именно делает. Удалил JII — система в
полном порядке, всё установленное живёт в своих родных менеджерах.

Цифры (на июль 2026): **~19 000 строк Rust**, один бинарник, **17 источников**,
**297 юнит-тестов**, **70 задокументированных архитектурных решений (ADR)**,
полная локализация **en + ru** (383 ключа), релизы `v0.1.10-beta`.

## 2. Философия и принципы (почему JII такой)

1. **Пользователь думает о софте, не о менеджерах.** «Хочу Docker» → JII решает
   *как* и объясняет *почему*.
2. **Объяснимость.** Каждая рекомендация несёт причины («официальный пакет Fedora»,
   «свежее, но неподписанное»). Никакого скрытого ML — ранжирование детерминировано.
3. **Безопасность не продаётся за удобство.** Три уровня доверия; авто-режим никогда
   не ставит недоверенное; root — только на конкретные шаги и с показом команд.
4. **Никогда не прятать источник.** Пользователь всегда видит, откуда придут байты.
5. **Всё превьюится.** Любое действие сначала строит план; `--dry-run` показывает его
   целиком, включая root-шаги.
6. **Никаких тупиков.** Отказ без предложения — баг. Не нашли пакет → даём ссылки
   на поиск; нет менеджера → предлагаем его поставить; ошибка → печатаем «что делать»
   (`JiiError::remedy()`, ADR-0032).
7. **Минимум шума, но не тишина.** Тихий терминал не должен выглядеть зависшим —
   всегда есть спиннер/прогресс. Успех — одна строка, а не простыня.
8. **JII сотрудничает с системой, а не становится её центром** (ADR-0048). Он
   уважает чужие менеджеры, не трогает их базы напрямую и оставляет систему
   консистентной, даже если JII удалить.

## 3. Как это работает: единый конвейер

Каждая команда — один и тот же ментальный конвейер:

```
Запрос → search → rank → plan → execute → Итог
         параллельный  приоритет+  ПЛАН —     root только
         опрос всех    доверие     объект     на нужные шаги,
         источников                первого    реестр пишется
                                   класса     только при успехе
```

- **search** — движок (`engine/mod.rs`) параллельно (tokio) опрашивает все доступные
  провайдеры, у каждого свой таймаут. Упавший источник помечается «✗ timeout» и не
  валит поиск. Результаты кэшируются; при недоступности источника отдаётся
  устаревший кэш (stale-on-error, ADR-0010). У постоянно падающего источника
  срабатывает «предохранитель» (circuit breaker, ADR-0044) — его временно не трогаем.
- **rank** — `engine/ranking.rs` сортирует кандидатов: первичный ключ — приоритет
  источника из конфига, тай-брейк — доверие; профиль может подвинуть (например,
  `sandbox` поднимает Flatpak). Перед сортировкой срабатывает junk-фильтр
  (см. §8.3). GitHub — намеренно **строго последний** (сырой бинарник — крайний
  случай).
- **plan** — провайдер строит `InstallPlan`: список декларативных `Action`
  (выполнить команду / скачать / распаковать / положить файл), размер загрузки,
  верификация, причины рекомендации. **План никогда сам не выполняется** — его можно
  показать (`--dry-run`), подтвердить, отклонить.
- **execute** — `exec.rs` — единственное место, где план превращается в эффекты.
  Root-шаги эскалируются батчем через `privilege.rs` (sudo на TTY, pkexec без),
  каждая команда печатается ровно так, как выполняется. Реестр (`registry.rs`)
  пишется **только при успехе**.

`install`, `remove`, `update`, `search`, `info`, `how` — все читают один и тот же
конвейер, просто останавливаются на разных стадиях.

конкретных источников. Декларативные TOML-источники (`data/sources/*.toml`)
запланированы, но пока не построены.

## 5. Ключевые абстракции (что рассказывать про «как устроено»)

### Трейт `Provider` — один контракт для всех источников

Обязательные методы: `id`, `trust`, `is_available` (есть ли бинарник/сеть),
`search`, `plan_install`, `plan_remove`, `plan_update`, `list_installed`.

**Рост через опциональные методы с дефолтами (ADR-0022)** — так трейт расширяется
без «толстого интерфейса» и без ветвлений в ядре: `plan_install_many` (батч одним
транзактом), `plan_update_all` (обновление всей системы), `describe` (карточка
`info`), `ecosystem` (метаданные для bootstrap менеджера), `can_search` (сетевой
реестр без локального CLI), `launch_command` (`--run`), `probe` (здоровье),
`is_installed`. Провайдер, который чего-то не умеет, просто наследует дефолт.

**Железный контракт:** провайдер **планирует, но никогда не исполняет**
привилегированное. Исполнение и root — только в `exec.rs`/`privilege.rs`.

### `PackageCandidate` → `InstallPlan` → `Action`

- `PackageCandidate` — найденный вариант: имя, источник, версия, доверие, подпись,
  описание, популярность, флаг подозрительности + непрозрачный `raw` (провайдерский
  payload для plan-стадии; ядро в него не заглядывает).
- `InstallPlan` — план: список `Action`, размер загрузки, **причины рекомендации**.
- `Action` — декларативный шаг: `RunCommand {argv, needs_root}` / `Download {url,
  verify}` / `Extract` / `Place` / `RemoveFile` / `Replace` (атомарная подмена для
  self-update). Никакого «сделай что угодно» — у каждого варианта свой обработчик.

### Спецификация пакета — язык JII (ADR-0031)

`name[:source][@ref]` — например `htop:pipx`, `firefox:flatpak`,
`sharkdp/bat` (GitHub-репозиторий), `node@20`. Всё, что «принадлежит пакету»,
выражается в спеке, а не флагами.

## 6. Ранжирование (почему рекомендуется именно это)

1. **Жёсткие фильтры до скоринга:** несовместимая архитектура — вон; недоверенное в
   `--auto` — вон.
2. **Первичный ключ — приоритет источника** из конфига (по умолчанию: нативный
   менеджер дистрибутива → copr → flatpak → snap → реестры языков (cargo/npm/pipx/go)
   → brew/nix → **github последним**). Детерминировано и объяснимо.
3. **Тай-брейк — доверие** (official > community > untrusted).
4. **Профили**: `stable` (дефолт), `sandbox` (поднимает Flatpak); `latest`/`minimal`
   зарезервированы, пока нет сравнимых данных о версиях/размере.
5. **Причины обязательны** — каждая рекомендация объясняет себя.

Почему GitHub последний: это не пакетный источник, а сырой бинарник без менеджера —
без авто-обновлений, без подписи дистрибутива. Он полезен как **последний шанс**
(программы, которых нигде больше нет), и именно так позиционируется.

## 7. Модель безопасности (самая важная тема для вопросов)

### 7.1 Три уровня доверия

| Уровень | Примеры | Поведение |
|---|---|---|
| 🟢 `official` | репы дистрибутива (dnf/apt/pacman/zypper/xbps/portage) | Ставится по Y, включая `--auto`. |
| 🟠 `community` | COPR, Flathub, Snap, AUR, crates.io/npm/PyPI, Nixpkgs, brew | Ставится, источник всегда показан; порог подтверждения настраивается. |
| 🔴 `untrusted` | GitHub-бинарник, пакеты-сквоттеры | **Всегда явное подтверждение**, даже с `--auto`. |

`default_yes` — **порог по доверию** (`default_yes_max_trust`), не глобальный
булев: выше порога промпт дефолтится в «да», ниже — JII всё равно спрашивает.
**Авто-режим никогда не ставит untrusted** — это неизменяемое правило (ADR-0006).

### 7.2 Root-модель

JII **никогда не работает целиком под root**. Только конкретные шаги плана
(например, `dnf install x`) эскалируются — батчем, один запрос пароля, с показом
точных команд заранее. Провайдеры физически не могут выполнить привилегированное —
у них нет доступа к privilege-слою. Минимальная поверхность атаки (ADR-0005).

### 7.3 Junk-фильтр — защита от пакетов-сквоттеров (ADR-0067)

Проблема: в реестрах языков имя «htop» может занять чей-то учебный проект. Раньше
`jii htop:pipx` честно ставил этот мусор.

Решение: перед ранжированием `mark_suspicious` понижает до `untrusted` кандидата из
сетевого реестра, если он выглядит сквоттером: скачиваний < 1000 в месяц
(crates.io/npm), либо — когда популярность недоступна — нет описания / версия
`0.0.x` / провайдер сам пометил (PyPI: единственный релиз старше 5 лет). Результат —
красное предупреждение и ручное подтверждение, авто-режим такое не выберет.

Почему **предупреждение, а не блокировка**: JII не может знать наверняка, что пакет
мусорный, а тупики запрещены философией. Официальные источники и path-подобные имена
(`owner/repo`) фильтр не трогает никогда.

### 7.4 Верификация артефактов

Где источник даёт возможность — проверяем: sha256 у GitHub-релизов (до использования
байтов), подписи RPM/deb — на стороне менеджера, checksum крейтов — у cargo.
Нет подписи → пометка «unsigned» и повышенный барьер. Факт верификации записывается
в реестр (`jii list --audit` показывает).

### 7.5 Скрипты brew/nix

Официальные инсталляторы Homebrew/Nix — это «curl | bash». JII не запускает их
молча: показывает скрипт **целиком**, спрашивает явно (и `--auto`/`--yes` согласием
НЕ считаются), выполняет без эскалации. Не-TTY — только печатает команду.

## 8. UX-механики (что делает JII приятным)

- **`jii doctor`** — интерактивный помощник: здоровье источников, проверки системы
  (PATH, токен GitHub, Flathub), курируемые советы под дистрибутив (кодеки, RPM
  Fusion) с пропуском уже сделанного; каждое действие — превью и согласие.
- **`jii setup`** — первый запуск: выбор режима вывода (Friendly/Advanced) и языка;
  срабатывает до любой команды один раз (ADR-0051).
- **Чузер** — если кандидатов несколько и однозначного лидера нет: меню со
  стрелками, Enter **и мышью**; скроллится на низких терминалах.
- **Опечатки** — точное совпадение сначала, на промахе расширение (префикс,
  хвостовая опечатка, середина слова — `firefx` → `firefox`).
- **Полный промах** — не тупик: ссылки на поиск GitHub/Flathub.
- **`jii how <name>`** (алиас `why`) — почему/как это установлено; показывает **все**
  копии имени, если оно стоит из нескольких источников.
- **`jii update`** — вся система: агрегирует bulk-обновление каждого менеджера +
  обновляет сам JII последним; тихий прогресс со сводкой «сколько пакетов обновилось
  на каждом источнике»; ошибки источников не молчат — код выхода ненулевой.
- **`--run`** — запустить программу сразу после установки (или просто запустить,
  если уже стоит); Flatpak сам знает, что запуск — это `flatpak run <id>`.
- **Bootstrap менеджера (T6, ADR-0065)** — `jii obsidian` на машине без Flatpak
  предложит: «поставить Flatpak и затем приложение?» — вместо падения в GitHub.
  Менеджер ставится только через источник, который реально работает здесь.
- **Локализация** — целиком en/ru, включая ошибки и промпты; `д/н` работают как `y/n`.
- **`--json`** — стабильные машинные схемы для скриптов; `--dry-run` — везде.

## 9. Самообновление (ADR-0040)

`jii` — зарезервированное имя самого инструмента:

- `jii update jii` — проверяет новейший релиз; если стоит user-space бинарник —
  скачивает musl-tarball, сверяет sha256 и **атомарно подменяет сам себя** (без
  root); если стоял пакетом — предлагает путь через dnf/apt.
- Сравнение версий честное: «другой опубликованный тег» = «есть обновление»,
  без хрупкого семвер-угадывания; если тег выглядит **старше** текущего — JII
  предупреждает о даунгрейде до вопроса.
- `jii uninstall` — удаляет JII тем же способом, каким он был установлен.

## 10. Дистрибуция JII

- **Однострочник:** `curl -fsSL https://raw.githubusercontent.com/0nigiris/JII/master/install.sh | sh`
- **Релизы GitHub:** статический musl (x86_64 + aarch64) — работает на любом glibc/musl
  дистрибутиве; tarball + `.rpm` + `.deb` + sha256, собирается CI по тегу.
- **Рецепты** в `packaging/`: COPR spec, AUR PKGBUILD, brew formula, nix, alpine,
  void, gentoo — «сапожник в сапогах»: JII распространяется теми же каналами,
  которые рекомендует.

## 11. Скрытая команда тестера

`jii yes-I-am-dev-and-want-to-test` — спрятана из `--help` и README (есть только в
`docs/TESTING.md`). Для добровольцев, гоняющих JII в свежих VM:

12 сценарных шагов (doctor, поиск с junk-эвристиками, info, **реальная** установка
htop, list/how, update, **реальное** удаление, тупик на несуществующем имени,
отклонение `npm@1.0`, sources). Перед шагом — что ожидать; после — вердикт
`[Y/n/s]`. Всё пишется в лог с **вычищенными username/hostname**; в конце — загрузка
лога на 0x0.st (с фолбэком) в одно нажатие и **предзаполненная ссылка на GitHub
issue** с таблицей PASS/FAIL. Любой FAIL → ненулевой код выхода (для скриптов).

## 12. Качество: тесты, CI, правила работы

- **297 юнит-тестов**: все парсеры гоняются на фиксированных сэмплах вывода
  (правило «изолируй парсеры»); ранжирование, junk-фильтр, spec-грамматика, i18n
  en/ru-паритет, планы провайдеров.
- **CI** (`ci.yml`): `cargo clippy -D warnings` + `cargo test`, оба `--locked`,
  на каждый push/PR. Definition of Done: clippy чистый, тесты зелёные, поведение
  проверено минимум через `--dry-run`.
- **Релизный CI** (`release.yml`): тег `v*` → cross-сборка musl → 12 артефактов.
- **AI Handoff Policy** (CLAUDE.md): проект продолжаем **любым** агентом — после
  каждой сессии обновляются TASKS/AI_CONTEXT/DECISIONS; знание не живёт в чатах,
  только в репозитории (ADR-0011).

## 13. Дайджест важнейших решений (ADR) — «почему так, а не иначе»

| Решение | Почему |
|---|---|
| **Rust** | Один статический бинарник без рантайма (критично для установщика — он должен работать на голой системе), скорость старта, надёжность типов для parsing-heavy кода. |
| **Один crate, не workspace** (ADR-0001) | YAGNI: границы держат модули; workspace — когда реально вырастем. |
| **JSON-реестр, не SQLite** (ADR-0002) | Сотни записей, не миллионы; человекочитаемо; API реестра спроектирован так, что миграция на SQLite ничего не сломает. |
| **`Plan` — объект первого класса** (ADR-0003) | Всё превьюится, `why`/`--dry-run`/выполнение читают один объект — невозможно «показать одно, сделать другое». |
| **Ядро не ветвится на источник** (ADR-0004) | Вся специфика — в провайдерах; новый источник не трогает ядро. Тест-инвариант проекта. |
| **Никогда целиком root** (ADR-0005) | Минимальная поверхность атаки; root — свойство шага, не программы. |
| **`Action`-enum вместо «сырых команд»** (ADR-0007) | Нет универсального «выполни что угодно»; у Download принудительная верификация. |
| **Версия — строка, не semver** (ADR-0009) | Реальные версии пакетов (dnf epoch, дата-теги) семвером не парсятся; честная строка лучше ломкой магии. |
| **Машинный вывод инструментов** (ADR-0012) | `dnf5 --queryformat`, `flatpak --columns`, zypper XML: человеческий текст меняется, машинный — контракт. |
| **Рост трейта опциональными методами** (ADR-0022) | Возможности добавляются без поломки существующих провайдеров и без жирного интерфейса. |
| **Platform = факты, не политика** (ADR-0029) | Провайдер самоотключается по отсутствию своего бинарника; «поддерживается ли дистрибутив» — вопрос «есть ли хоть один источник», а не `if fedora`. |
| **Форж-абстракция** (ADR-0049) | GitHub — не исключение, а одна реализация `Forge`; Codeberg/GitLab добавляются трейтом. |
| **i18n ключами** (ADR-0050) | Строки в TOML, вшиты в бинарник, деградация en → ключ, паника невозможна. |
| **GitHub строго последний** (ADR-0061) | Решение владельца: сырой бинарник — крайний случай после всех настоящих пакетных источников. |
| **Junk-фильтр = предупреждение, не блок** (ADR-0067) | Эвристика может ошибаться; тупики запрещены. Понижение доверия даёт и защиту (авто не возьмёт), и свободу (явно — можно). |
| **Windows/macOS — только план** (ADR-0068) | Три волны, macOS первой (brew уже есть → самый дешёвый порт); код не пишем, пока Linux-ядро не устаканится. |

## 14. Статус и планы

**Сейчас:** `v0.1.10-beta`. Linux-ядро функционально полное: 17 источников, батчи,
системное обновление, self-update, doctor, локализация, junk-защита, тестерская
команда, **живые прогресс-бары** (проценты из вывода источника, ADR-0069). Владелец
активно тестирует на Fedora/Ubuntu/Arch/openSUSE/Void/Gentoo/Nix.

**Известный баг (не исправлен, кандидат в следующий релиз):** `jii install` может завести
в тупик («Skipped …»), если лучший кандидат — из неустановленного менеджера (например Snap),
а поднять этот менеджер не удалось: вместо отката на уже показанную альтернативу
(cargo/npm/pipx/brew) пакет просто пропускается. Причина — цикл установки хранит только одного
«лучшего» кандидата на пакет и отбрасывает альтернативы до шага bootstrap. Чинится протаскиванием
альтернатив и повтором с следующим доступным кандидатом.

**Впереди:**
- Обкатка внешними тестерами (VM-матрица дистрибутивов) → стабильная бета.
- Публикация в COPR/AUR под аккаунтами владельца.
- Декларативные TOML-источники (добавлять простые репы без перекомпиляции).
- Лендинг + материалы к запуску (Hack Club Star Dance, Beest и другие площадки).
- macOS (волна A), затем Windows (волна B) — по плану ADR-0068.
- Фоновое авто-обновление системы; выбор portable-vs-native при self-update (бэклог).

## 15. FAQ — готовые ответы на вероятные вопросы

**— Чем JII отличается от apt/dnf/pacman?**
Ничем не конкурирует — он их **использует**. apt знает только свои репы; JII ищет по
всем источникам сразу, выбирает лучший и делегирует установку родному менеджеру.

**— Чем отличается от Flatpak/Snap?**
Это форматы пакетов со своими магазинами. Для JII они — два из 17 источников.

**— А от topgrade / pacstall / deb-get / nala?**
topgrade только обновляет (JII — ищет/ставит/объясняет/обновляет); pacstall/deb-get —
однодистрибутивные обёртки над одним типом источника. Ближайший аналог по духу —
поиск Zypper/PackageKit, но кросс-источникового установщика с моделью доверия и
объяснимым ранжированием среди известных нам нет.

**— Это безопасно? Вы качаете случайные бинарники?**
Наоборот: сырые бинарники (GitHub) — принудительно последние в рейтинге, всегда
`untrusted`, всегда явное подтверждение, sha256 сверяется. Дефолтная рекомендация —
официальный репозиторий дистрибутива. Root — только на конкретные показанные шаги.
Авто-режим физически не может поставить недоверенное.

**— Что будет, если удалить JII?**
Ничего: всё установленное живёт в родных менеджерах и продолжает обновляться ими.
JII хранит только свой JSON-реестр намерений.

**— Почему Rust?**
Установщик должен работать на «голой» системе → один статический musl-бинарник без
зависимостей и рантайма; плюс скорость старта и типобезопасность для кучи парсеров.

**— Как вы решаете, что рекомендовать?**
Детерминированный рейтинг: приоритет источника (конфигурируем) → доверие → профиль.
Без ML, каждая рекомендация печатает свои причины. Одинаковый ввод → одинаковый ответ.

**— Пакет с таким именем есть в npm, но это мусор. Что будет?**
Junk-фильтр: почти нулевые скачивания / нет описания / заброшен годами → кандидат
падает в `untrusted` с красным предупреждением; авто-режим его не возьмёт.

**— Сколько дистрибутивов поддерживается?**
Семейства Fedora, Debian/Ubuntu, Arch, openSUSE, Void, Gentoo — нативно; плюс
дистро-независимые источники (Flatpak, Snap, cargo/npm/pipx/go, brew, Nix, GitHub)
работают везде. Провайдер сам определяет, применим ли он — по наличию своего
инструмента, не по имени дистрибутива.

**— Один бинарник? Сколько весит установка?**
Да, один статический бинарник (LTO + strip), ставится в `~/.local/bin` без root.

**— Кто это писал?**
Проект разрабатывается в паре «владелец + AI-агент» с жёсткой дисциплиной: канон в
docs/, 68 ADR, политика хендоффа — любой агент (человек или AI) может продолжить с
минимальной потерей контекста. Все решения и их причины — в репозитории.

**— Можно добавить свой источник?**
Да: реализуешь трейт `Provider` (8 обязательных методов) — ядро трогать не нужно.
В планах декларативные TOML-источники вообще без кода.

**— Windows/macOS будут?**
План есть (ADR-0068): macOS первой (Homebrew-провайдер уже написан), Windows следом
(winget/scoop). Код начнём, когда Linux-бета стабилизируется.
